# 电商商品上新 AI 工作流

一个可运行的个人演示：把商品资料转换成**待审核**的电商商品文案。项目以虚构商品为例，展示资料校验、提示词设计、模型调用、结构化输出检查和人工审核。不会登录店铺、读取订单或自动发布商品。

包含 [Dify 可视化工作流](dify/README.md)：已在 Dify Cloud 导入并使用虚构资料测试，测试中发现模型仍会添加未获证实的描述，所有输出必须人工核查。

```text
商品资料 JSON → 必填字段检查 → 组装提示词 → 大模型生成 JSON
             → 结构/证据引用检查 → 风险词提示 → 人工审核
```

## 解决什么问题？

电商运营上新时需要整理商品名称、规格、卖点等，再撰写标题和描述。本项目把这些步骤整理成可复现的流程，输出标题、卖点、商品描述、需要补充的信息与审核提示。所有卖点和描述都带输入事实的引用 ID，便于人工回查。

**事实 ID 存在不代表引用内容一定支持文案。** 模型可能误解或编造，风险词检查也只能发现预设词汇；发布前必须人工核对事实、平台规则、商标和广告表述。

## 直接运行：离线演示

需要 Python 3.10+，无第三方依赖。以下命令在仓库根目录执行：

```bash
python workflow.py examples/product.json --mode demo --output result.json
python -m unittest discover -s tests -v
```

`demo` 使用预写的模拟模型响应，不调用 AI，目的是在没有账号和 API 密钥时演示流程与校验逻辑；示例结果不代表模型实际效果。

## 可选：接入真实模型

使用支持 `chat/completions` 请求格式的模型服务，按服务商文档获取**完整 HTTPS 接口地址**、模型名与 API 密钥：

```powershell
$env:LLM_API_URL = 'https://你的服务商完整地址/v1/chat/completions'
$env:LLM_MODEL = '你的模型名称'
$env:LLM_API_KEY = '你的密钥'
python workflow.py examples/product.json --mode live --output result.json
```

`live` 会将商品资料和提示词发送给配置的模型服务商，并可能产生费用；请仅输入有权发送的数据，检查服务商价格与数据处理政策。不要把真实密钥写入代码、提交到 GitHub 或发给他人。接口只支持示例中的 Chat Completions 消息格式，兼容性取决于服务商；该项目未对各服务商做兼容性验证。

真实模型可能输出无效 JSON、缺少字段或虚构的事实 ID：程序会报错停止，不会把这些结果视为审核通过。当前没有 JSON 自动修复和重试。

## 输入与输出

参照 `examples/product.json`：每条商品事实需要唯一的 `id`、`label` 和 `value`。`missing_information` 是人工已知缺失的信息；程序不会要求模型补造。实际输出包括：

- `title`：标题草稿。
- `selling_points`：卖点及对应的 `evidence_ids`。
- `description`：详情文案及对应的 `evidence_ids`。
- `missing_information`：资料中仍待确认的信息。
- `review`：固定人工审核状态、标题长度、预设风险词和证据核对提示。

固定长度上限与风险词只是**示例配置**，不代表任何平台规则或法律意见。最终判断由运营或审核人员作出。

## 面试时怎么讲

可以从“输入—处理—输出—异常—人工审核”讲完整流程：

1. 输入是什么？为什么给事实设置 ID？
2. 为什么把商品内容当数据，而不当作模型指令？
3. 模型没按 JSON 输出、引用不存在的事实、或缺少资料时怎么处理？
4. 风险词检测能发现什么、不能发现什么？
5. demo 与 live 有什么区别？为什么不能把演示结果说成实际模型评测？

这是在 AI 协助下制作的个人学习项目；简历中只写自己真正理解、运行和参与改进的部分。它并未接入 Dify、Coze、RAG、真实店铺或商品发布接口，也没有真实用户和业务提效数据。
